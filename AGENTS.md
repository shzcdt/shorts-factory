# AI Rules — ClipPilot

Этот файл — единственная истина о том, как ИИ-ассистент работает над проектом.
Все остальные инструкции подчиняются этим правилам.

---

## 1. Контекст проекта

**ClipPilot** — локальный автопилот для превращения длинных видео в YouTube Shorts.

- **Стек**: Python 3.12+ (совместимо с 3.14), SQLite, ffmpeg, watchdog, YouTube Data API v3
- **Архитектура**: CLI-приложение (`python -m clip_pilot ...`), src-layout в `src/clip_pilot/`
- **Хранилище состояний**: SQLite (`data/db.sqlite3`) — единственный источник правды
- **Конфигурация**: `config.yaml` + `.env` (секреты)
- **Пайплайн**: `source → analyze → cut → format → review? → publish`
- **MVP-принцип**: делаем минимально работающий вертикальный срез, не строим космический корабль

---

## 2. ГЛАВНОЕ ПРАВИЛО — Без разрешения ничего не трогать

> **Запрещено создавать, изменять или удалять файлы без явного одобрения пользователя.**

Это означает:
- ❌ Нельзя писать код сразу в файлы — только предлагать в чате.
- ❌ Нельзя запускать `pip install`, миграции, `ffmpeg` без команды.
- ❌ Нельзя переименовывать/удалять существующие файлы.
- ✅ Можно читать файлы, анализировать, задавать вопросы.
- ✅ Можно предлагать изменения блоками кода с указанием пути.
- ✅ Можно создавать файлы **только после фразы пользователя** вроде "делай", "ок", "применяй", "согласен".

**Исключение**: если пользователь явно сказал "сделай как считаешь нужным" — можно действовать, но с откатом.

---

## 3. Процесс работы над задачей

Для каждой задачи (T1, T2, ...) соблюдай цикл:

1. **Анализ** — прочитай существующий код, пойми контекст.
2. **Предложение** — покажи, что собираешься сделать:
   - Список файлов, которые будут созданы/изменены
   - Ключевые решения и почему именно так
   - Риски и альтернативы
3. **Ожидание ОК** — стоп, пока пользователь не одобрит.
4. **Реализация** — после одобрения выдай финальный код.
5. **Саммари** — в конце обязательно (см. раздел 4).

Если задача большая — разбивай на шаги и согласовывай каждый.

---

## 4. Формат саммари после каждого одобренного изменения

В конце каждого изменения **обязательно** выдай блок в таком формате:

📋 Саммари изменения
Что сделано:
Краткий список действий (3-7 пунктов)
Затронутые файлы:
path/to/file1.py — что изменилось
path/to/file2.py — что изменилось
Как это работает:
Объяснение логики работы на 5-10 строк. Как новые куски кода связаны
с существующими. Куда смотреть, если что-то сломается.
Как проверить:
Команды для smoke-теста (например, python -m clip_pilot --version).
Что дальше:
Следующий логичный шаг (обычно — следующая задача из бэклога).

## 5. Стиль кода

- Python 3.12+ — используй современные фичи (type hints, `|` для Union, dataclasses).
- Строгая типизация везде, где это не overkill.
- Docstring на публичных функциях (Google-style).
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов.
- Константы — `UPPER_CASE` в `config.py` или `constants.py`.
- Не используй `*args`, `**kwargs` без крайней необходимости.
- Магические числа — только через `config.yaml` или именованные константы.

---

## 6. Зависимости — минимизировать

- Не добавляй библиотеки без обсуждения.
- Каждая новая зависимость = риск конфликтов + размер venv.
- Сначала проверь, нельзя ли обойтись стандартной библиотекой.
- Если библиотека нужна — предложи альтернативы и обоснуй выбор.

---

## 7. Специфика проекта — что важно помнить

- **Видео = тяжёлые файлы.** Всегда думай о дисковом пространстве и I/O.
- **SQLite = однопоточная запись.** Используй WAL-режим, busy_timeout, короткие транзакции.
- **ffmpeg = subprocess.** Обрабатывай stderr, логай команды, проверяй коды возврата.
- **YouTube API = квоты.** 1600 единиц на загрузку, 10 000 в сутки. Учитывай всегда.
- **Windows-совместимость.** Проект должен работать на Windows — пути через `pathlib`, UTF-8 везде.
- **Логирование — обязательно.** Любое действие с сущностью (source/clip/post) пиши в лог с ID.

---

## 8. Чего НЕ делать

- ❌ Не переписывать работающий код "чтобы было красивее" без запроса.
- ❌ Не добавлять функционал "на будущее" — только то, что нужно для текущей задачи.
- ❌ Не использовать async без причины (для MVP достаточно sync).
- ❌ Не хардкодить пути, токены, лимиты — всё в `config.yaml` или `.env`.
- ❌ Не писать "потом оптимизируем" — делай сразу приемлемо.
- ❌ Не предлагать миграции на PostgreSQL/Redis "на вырост" — SQLite достаточно.

- Если задача выходит за рамки текущего спринта — предупреди и предложи вынести в бэклог.
